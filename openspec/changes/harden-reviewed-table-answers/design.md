# Design

## Context

동기와 범위는 proposal.md를 따른다. 이번 변경은 데이터 계약과 여러 모듈을 함께 바꾸므로
설계 문서가 필요하다. 현재 `Block.table`은 문자열 행렬이지만 `make_chunks`는 블록 본문을
합쳐 전달한다. `validate_answer`의 숫자 집합 포함 검사는 항목과 수치의 관계를 검증하지 않는다.
검토 설정은 원본 해시에 묶여 있으나 검토자 유형과 사실 관계를 표현하지 않는다.

현재 관찰한 결함은 `docs/code-review-2026-10-08.md`의 10개 항목과 대응한다.
이전 조사에서 기본 55개 테스트는 통과했고 별도 리뷰 테스트 12개는 실패했다. 이는 이번 변경의
검증 결과가 아니다. 과거 로컬 판정의 답변 가능 사례는 9/10이며 15/16은 다른 분모의 값이다.
기존 파싱 검사도 문자열 포함만 보므로 표 관계·원문 대조를 대체할 수 없다.

개발 절차의 근거는 `docs/manual-preanalysis-handoff.md`다. 이 계획을 작성하면서 새 원문
사전 분석이나 사후 대조를 완료한 것은 아니다. 기존 6개 부분 검토 페이지·13개 청크 기록도
전체 436페이지 검토로 확대 해석하지 않는다.

## Goals / Non-Goals

**Goals:**
- 원문 검토가 데이터 계약의 실제 입력이 되며 원본부터 최종 수치 인용까지 관계를 추적한다.
- 표 수치의 재작성 가능성을 줄이고 적용 조건·필수 경고를 프로그램이 함께 출력한다.
- 기존 결함 10개를 회귀 검사와 관찰 가능한 상태·사유로 연결한다.
- 원문 검토, 자동 계약 검사, 검색 성공, 답변 의미 판정을 별도로 기록한다.

**Non-Goals:**
- 범용 표 의미 인식, 모든 자연어 수치의 자동 구조화, 단위 환산·계산·정비 권고 추론.
- 추가 LLM 검증 서비스, 별도 벡터 DB, LangChain 또는 전체 매뉴얼 일괄 승인.
- 모델의 사실 선택이나 일반 문장의 의미가 항상 정확하다는 보장.

## Decisions

### 1. 원문 분석을 구현의 선행 단계로 둔다

`사전 분석 → 규칙/계약 확인 → 구현 → 동일 원문 대조 → 색인/답변 평가` 순서를 따른다.
사전 분석 기록 없이는 파서·청크 규칙 구현 단계로 넘어가지 않는다. 시작 대상은 기존 PDF
13·16 표, 200·205·207·208·212의 다단/경고/적용 범위, 6의 빈 페이지다. 연결된 필수 내용이
다른 페이지에 있으면 해당 페이지만 추가한다. 없는 유형이나 해석 불가 영역은 미확인으로 남긴다.

기록에는 문서/차량/출처 상태, SHA-256, 전체 페이지 수, PDF/인쇄 페이지, bbox와 좌표계,
읽기 순서, 표 관계, 경고 적용 범위, 사양 판정 근거, 필수 연결, 미확인 사항, 검토자·유형·날짜를 둔다.
PDF 좌표는 pdfplumber의 x0/top/x1/bottom, point 단위로 기록하며 이미지 pixel과 구분한다.
상세 기록은 `data/reviews/`와 로컬 제외 경로, 공유 가능한 규칙 요약은 docs에 둔다.

구현 후 같은 원문의 Page/Block/Chunk/fact를 대조한 기록은 원본·처리 계약·검토 설정 해시에
묶는다. 대조용 후보 생성과 답변용 승인 상태를 구분하고, 영향받는 묶음은 사후 대조가 끝난 뒤
색인 승인한다. 해시가 달라지면 이전 승인 기록을 그대로 재사용하지 않는다.

대안은 구현 후에만 표본 확인하는 방법이다. 빠르지만 표의 관계를 추측해서 계약을 만드는
문제가 남으므로 사용자가 선택한 선행 분석 방식을 채택한다. 에이전트도 검토할 수 있으나
`reviewer_type=agent`를 남기고 독립적인 사람 검토로 표시하지 않는다.

### 2. 버전이 있는 표 사실 계약을 기존 검토 자료에서 공급한다

`contracts.py`에 명시적인 계약을 두고 `parsing.py`가 로컬 검토 설정을 변환한다.
아래는 제안 필드이며 실제 원문 값은 소스 코드에 넣지 않는다.

| 계약 | 주요 정보 |
| --- | --- |
| PageRef | pdf_page, printed_page(미확인은 null), section, block/region reference |
| ReviewRecord | 원본 해시, 검토 설정 버전, reviewer, reviewer_type, reviewed_on, analysis reference |
| TableFact | fact_id, subject, attribute, condition key/표시문, applicability, quantities, source refs, required refs |
| Quantity | value_text, unit_text, qualifier(정확값/범위/상한/하한 등), 원문 셀/영역 참조 |
| EvidenceLink | target_id, required 또는 optional, 역할(머리글/각주/경고/관련 행) |

값은 부동소수점으로 재해석하지 않고 원문 표현을 보존한다. 복수 단위는 원문에서 확인된
대응만 저장하며 자동 환산하지 않는다. 사실 ID는 원본·위치·정규화된 의미 필드·계약 버전에서
결정적으로 만들고, 처리 세대와 검토 이력은 별도로 연결한다. 내용 변경 시 ID 또는 세대가 바뀐다.

행/열 위치와 bbox는 모두 선택 가능한 출처 수단이지만 값·머리글·각주 관계를 원문에서
찾을 수 있는 정보는 필수다. ID·자료형·해시·출처 범위·참조 존재·검토 이력은 자동 검사한다.
원문 의미 일치는 사전/사후 검토로 확인한다. 검토된 관계 없이 `table` 행렬에서 사실을 자동 승인하지 않는다.

대안은 매 질의마다 LLM으로 표를 해석하거나 범용 자동 표 파서를 추가하는 것이다. 전자는
비용과 변동성이 있고 후자는 이번 대표 매뉴얼 범위를 크게 넘으므로 기존 보정 설정 확장을 택한다.

### 3. 사실과 필수 맥락을 함께 검색한다

FAISS 검색은 기존 청크를 단위로 유지하며 승인 사실과 출처를 청크 메타데이터에 싣는다.
임베딩 본문은 검토된 대상·조건·값·단위를 결정적으로 포함하게 구성한다. 별도 fact 색인은
만들지 않아 검색·저장 경로를 늘리지 않는다. 단점은 큰 표 묶음의 검색 세밀도가 제한된다는 점이며
이번 원문 분석에서 의미가 완결되는 행/조건 묶음으로 경계를 정한다.

필수 연결이 미검토·다른 사양·unknown이면 해당 묶음을 제외하고 이유를 coverage에 남긴다.
다른 사양의 optional 링크는 제외하고 정상 묶음은 계속 처리한다. 필수/선택 구분 없는 기존
related_ids를 일괄 optional로 바꾸지 않고 원문을 보고 분류한다. 없는 ID·중복 ID는 입력 계약
오류로 거부한다. 정상 청크가 0개면 새 활성 색인을 게시하지 않고 이전 세대를 유지한다.

PDF와 인쇄 번호의 평행 목록은 PageRef 목록으로 교체한다. 인용도 같은 매핑을 사용한다.
파서·청크·사실 계약 버전을 processing fingerprint와 index metadata에 포함하고 로드 경계에서
검사한다. 구버전은 재생성을 안내하며 무검증 호환 기본값으로 승인하지 않는다.

### 4. 표 답변은 선택과 표시를 분리한다

모델 출력은 `table_fact`(evidence_id, fact_id)와 일반 설명용 claim을 구분한다. table_fact에는
모델 작성 text/value/unit/page 필드를 허용하지 않는다. 요청에 실제 포함된 ID 쌍만 스키마에
노출하고 후속 검사에서도 다시 대조한다. 표 수치 문장·조건·출처·필수 경고는 로컬 렌더러가 만든다.

표가 포함된 근거의 설명은 검토된 비수치 설명/경고 발췌 ID 선택으로 제한한다. 표 행과 수치
관련 문장을 일반 자유 주장 후보로 제공하지 않는다. 표와 일반 설명을 함께 묻는 요청에서는
일반 설명도 발췌 선택으로 구성해 자유 문장을 통한 표 수치 재작성 경로를 닫는다. 표와 무관한
일반 질문은 기존 생성 경로를 유지한다. 출력 유형은 모델의 자가 분류만 믿지 않고 제공한 근거
유형·허용 후보로 제한한다. 미구조화 표가 검색된 경우에도 같은 제한을 적용한다.

조건 키는 검토 자료에 정규화해 둔다. 별도 숫자 생성이나 자연어 조건 재작성을 허용하지 않는다.
첫 버전은 선택된 대상·항목에 여러 조건이 있으면 제공된 조건별 사실을 묶어 표시하거나
needs_clarification으로 유보한다. 일부 조건만 제공됐으면 전체 조건을 안다고 표시하지 않는다.
동일 대상·항목·차량·조건에 다른 값이 있으면 모델 선택 전에 충돌을 검사한다.

대안인 추가 LLM 판정은 주제/값 오연결을 확률적으로 탐지할 뿐이며 호출 비용·지연이 늘어난다.
사용자가 선택한 구조화+렌더링을 채택한다. 단, 모델이 잘못된 항목의 사실을 선택할 수 있으므로
최종 문장에 대상·조건을 숨기지 않고 사실 선택의 적절성을 별도 평가한다.

### 5. 발췌 누락과 문맥 부족을 관찰 가능하게 만든다

문장·행·구조 단위 후보를 만들고 1200자/32개 제한으로 뒤쪽 근거를 조용히 버리지 않는다.
표 사실과 필수 연결은 발췌 문장 분할과 독립적으로 제공한다. 후보 길이/개수 제한이 필요하면
제외한 근거 또는 원문 구간과 이유를 기록한다. 일반 발췌는 원문의 연속 구간이라는 조건을 유지한다.

문맥 예산에는 프롬프트·질문·출처·사실·발췌·스키마·출력 여유를 포함한다. 원문/저장 청크는
보존하고 완결된 묶음 단위로 선택한다. coverage에 selected/excluded ID와 reason을 추가한다.
아무 묶음도 못 담으면 모델 호출 없이 insufficient_evidence(reason=context_budget)를 반환한다.
일부 근거로 답해도 제외 목록과 처리 범위를 남긴다. 질문 자체가 예산을 넘으면 입력 오류다.

대안인 고정 글자 수 자르기는 단순하지만 조건·경고를 자를 수 있어 채택하지 않는다.

### 6. 실행 전 검사와 외부 예외 경계를 공통화한다

`pipeline.ask`와 평가의 질문 실행이 동일한 preflight를 사용한다. 순서는 입력 검사,
생성 설정 검사, 명시적 차량 충돌, 검색, 생성이다. 충돌 반환에 필요한 coverage는 로컬에서
읽을 수 있으면 포함하고 유료 조회는 하지 않는다. 보증 연도는 연식 패턴으로 보지 않으며
DCT 수동 모드와 수동변속기 차량을 구분한다. 불명확한 표현을 과도하게 충돌로 단정하지 않는다.
검색 전용 경로는 생성 모델을 요구하지 않는다.

SDK 3.26.0의 예외 계층을 실제 설치 코드로 확인하고 `OpenAIError` 계열의 예상 가능한 응답
검증 오류를 어댑터에서 단계별 RagError로 변환한다. 기존 transient 오류의 최대 2회 재시도와
deadline은 유지하고 인증·할당량 소진·잘못된 응답은 재시도하지 않는다. 임의 Exception 전체를
근거 부족으로 바꾸지 않는다. SDK 원문 오류에 포함될 수 있는 입력·헤더는 출력하지 않는다.

대안인 각 CLI/평가 호출부의 개별 catch는 정책이 달라질 수 있으므로 외부 어댑터와 공통
질문 실행 경계로 모은다.

### 7. 지표 계산과 평가 저장을 일관되게 한다

answerable은 expected_status=answered인 사례다. 분모는 그 전체 수, 분자는 실제 상태 일치와
유효한 pass 판정을 함께 만족한 수다. 검색 Recall@5도 같은 모집단을 사용한다. 모든 사례의
오류 수와 판정 완전성, 확인 요청의 적절성, 모든 근거 부족 사례의 유보를 별도 검사한다.

local/live/judge가 같은 파싱 검사 해석과 게이트 함수를 사용한다. 승인된 필수 파싱 검사
100% 통과, 답변 가능 Recall@5/답변 통과율 각각 90% 이상, 네 오류 종류 0, 유보 및 필요한
판정 완료를 함께 요구한다. 필수 검사 누락·0개 또는 answerable 0개는 통과가 아니다.
local은 답변 평가 미실행이므로 파싱 통과와 전체 게이트 미완료를 구분한다.

기존 16개 대표 사례를 유지하며 사실·조건·경고·출처의 기대 관계와 승인 기록을 추가한다.
문자열 존재 검사만으로 표 파싱을 통과시키지 않는다. 합성 경계 사례는 기본 pytest 회귀에
추가하고 `claude_test_*.py`는 `test_review_*.py` 계열로 옮겨 기본 수집에 넣는다.

평가 시작 때 로컬 보고서 실행 디렉터리를 만들고 각 사례 종료마다 원자적으로 checkpoint를
갱신한다. checkpoint는 완료 보고서의 active pointer로 게시하지 않는다. 예상 가능한 서비스
오류는 행으로 기록하고 계속한다. 완료 시 불변 detail/summary 세대로 게시한다. 프로세스
중단 시 마지막 checkpoint는 남지만 자동 재개·재과금 방지 기능까지 추가하지 않는다.
응답을 못 받아 알 수 없는 사용량은 unknown으로 남기며 0으로 추정하지 않는다.

CLI는 서비스 오류가 있는 실행을 결과 저장 후 비정상 종료로 전달한다. 미판정 live 결과와
판정 후 품질 실패를 구별하고, 명시적으로 실패한 local/judge 결과도 실패 코드로 전달한다.
과거 보고서의 재계산은 원본 해시/경로와 metric version을 가진 별도 로컬 결과로 저장한다.
과거 파싱의 문자열 검사 통과를 이번 관계 검증 통과로 승격하지 않는다.

대안은 전체 평가 끝에 한 번 저장하는 현재 방식으로, 도중 오류에 취약하므로 사례별 저장을 택한다.

### 8. 리뷰 항목과 설계 추적

| 리뷰 번호 | 처리 위치/결과 |
| --- | --- |
| 1, 7 | answerable 분자·분모, 파싱 포함 공통 게이트와 역사적 지표 정정 |
| 2, 6 | 발췌/문맥 제외 ID·이유, 완결된 묶음 선택과 부족 상태 |
| 3 | 검토된 사실 계약, 선택 ID 검증, 프로그램 수치 렌더링 |
| 4 | PageRef를 통한 PDF/인쇄 번호 대응 |
| 5, 10 | 공통 preflight와 사양 문맥 판정 |
| 8 | SDK 예외 변환, 사례별 checkpoint, CLI 실패 전파 |
| 9 | required/optional 링크 및 영향 묶음 제외 |

## Risks / Trade-offs

- 검토 자료 자체의 오해 → 원문 사전 분석과 구현 후 대조를 별개 기록으로 남기고 검토 유형을 공개한다.
- 올바른 값의 무관한 사실 선택 → 대상·조건을 출력하고 검색·선택·렌더링 평가를 분리한다.
- 발췌 방식으로 혼합 답변의 자연스러움 감소 → 수치 관계 보존을 우선하며 일반 질문 흐름은 유지한다.
- 조건 묶음과 경고로 문맥 증가 → 완결된 묶음 선택과 제외 사유를 기록하고 유보한다.
- 재생성 비용 → 동일 텍스트·임베딩 계약의 캐시만 재사용하며 추가 LLM 검증 호출은 도입하지 않는다.
- 유료 평가 → 기존 OpenAI 전송 범위 내 선택 텍스트만 전송하고 usage를 기록한다. 키 없는
  합성 회귀와 로컬 원문 대조를 먼저 수행하며 실제 모델 미실행을 통과로 바꾸지 않는다.
- 대표 영역 밖의 미검토 → 전체 처리 현황을 계속 표시하고 전체 매뉴얼 정확도를 주장하지 않는다.

## Migration Plan

1. 기존 원본 해시·활성 parsed/index 세대·검토 설정과 평가 기록을 확인하고 보존한다.
2. 사전 분석 기록을 완성하고 기존 검토 설정의 사실·링크·reviewer 정보를 새 계약에 맞춰 보완한다.
3. 새 코드로 파싱/청크 후보를 생성하고 동일 원문과 대조한다. 미확인 영역은 미승인으로 둔다.
4. 승인된 새 계약으로 ingest → index를 실행한다. 파서/청크/사실 계약 버전을 올리고 캐시
   재사용 조건을 확인한다. 원본 PDF나 기존 불변 세대를 덮어쓰지 않는다.
5. 합성 전체 회귀 → 원문 관계 검증 → 기존 16개 실제 모델 평가 → 의미 판정 순으로 확인한다.
   표 관계·수치·조건·경고 오류 0과 명세의 게이트를 만족해야 해당 실행을 통과로 보고한다.
6. 과거 지표는 별도 재계산하고 README/AGENTS/검증 요약에 계약, 명령, 처리 범위, 미검증을 기록한다.
7. 되돌릴 때는 구버전 코드와 그 코드가 읽을 수 있는 parsed/index 세대를 함께 복원한다.
   새 코드에 구버전 색인만 연결하는 방식은 호환성 검사로 거부한다. parsed와 index 포인터의
   두 번 교체를 하나의 트랜잭션이라고 주장하지 않으며 중간 불일치는 검색을 거부한다.
