# Design

## Context

동기와 기능 범위는 proposal.md를 따른다. 다음은 2026-10-07 탐색에서 확인한 사실이다.

- 구현 패키지·프로젝트 가상환경·의존성 설정·테스트가 아직 없다. 기존 참고 개발 문서는
  다른 프로젝트의 명령을 포함하므로 설치와 테스트 근거로 사용하지 않는다.
- 사용자가 차량을 2025 아반떼 N DCT로 확인했다. 대표 PDF는 16,757,322바이트이며 실제
  SHA-256 `87bbeec00684414edc31658bd0e104d714b35dab8fa8a46f68c35715a740bb0a`가 manifest와 일치한다.
- 기존 환경의 Python 3.11.9와 pypdf 6.19.0으로 확인한 페이지 수는 436이다.
  PDF 1~12, 13, 16페이지를 텍스트로 점검했으며 전체 시각적 검증은 하지 않았다.
  PDF 6페이지의 빈 추출 결과도 실제 빈 페이지로 확인된 것은 아니다.
- PDF 13/인쇄 1-7의 타이어 표에는 조건·앞뒤·각주가, PDF 16/인쇄 1-10의 오일 표에는
  수동·DCT 행과 공통 주의가 함께 있다. 페이지 11의 추출에는 중복된 도안 식별자와 제목이 보였다.
- manifest의 출처 주소는 `/manual/=ko_KR&...` 형태다. 누락 여부와 실제 접근성은 미확인이다.
- `.gitignore`가 `data/raw`를 제외하며 AGENTS.md가 원본 PDF 배포를 금지한다.

사용자는 빠른 구현을 위해 `text-embedding-3-small`, OpenAI 생성 API, FAISS 사용을 요청했다.
아래 설계는 이 결정을 반영한다. 생성 모델은 사용자 선택 `gpt-5-mini`이며,
실제 설치·호출·검증 결과는 하단 구현 버전과 검증 문서를 따른다.

## Goals / Non-Goals

**Goals:**

- 파서·저장소·모델 어댑터를 공통 계약으로 연결해 각 단계의 실패를 재현한다.
- 문서 한 권의 모든 페이지에 상태를 남기고, 검증 가능한 본문·표를 검색 가능한 근거로 만든다.
- 동일 원본과 설정을 반복 처리해도 중복을 만들지 않으며, 이전 정상 데이터 세대로 복귀할 수 있게 한다.
- 대표 질문 4개의 전체 흐름을 먼저 실행하고, 이후 전체 페이지와 16개 인수 평가로 확장한다.

**Non-Goals:**

- 임의의 모든 PDF 레이아웃을 자동 이해하거나 차량의 미확인 옵션을 추론하지 않는다.
- 생성 모델 또는 인용 검사만으로 의미적 정확성을 완전히 자동 증명하지 않는다.
- 분산 저장소·동시 다중 사용자·대규모 근사 최근접 검색은 설계하지 않는다.

## Decisions

### 1. Python CLI와 고정된 검색 후 생성 흐름

초기 지원·검증 버전은 Python 3.11.x로 제안한다. 현재 사용 가능한 3.11.9와 파서의 공식
지원 범위를 출발점으로 삼은 결정이며 다른 프로젝트의 최소 버전을 가져온 것이 아니다.
프로젝트 `.venv`를 만들고 `pyproject.toml`, 직접·전이 의존성이 고정된 설치 파일, README에
실제로 검증한 Python 패치 버전과 설치 명령을 기록한다. 상위 Python 버전 지원은 검증 전 주장하지 않는다.

기본 CLI는 `argparse`, 데이터 계약은 타입이 명시된 dataclass와 명시적 경계 검증,
벡터 검색은 `faiss-cpu`, 메타데이터는 JSON/JSONL, 테스트는 `pytest`를 사용한다.
PDF 처리는 `pdfplumber`, API는 공식 `openai` Python SDK를 직접 사용한다.
FAISS 입력 배열에는 `numpy`, 임베딩 입력 토큰 계산에는 `tiktoken`을 사용한다.
직접 HTTP 처리와 로컬 모델 설치 작업을 줄이고 단일 모델 제공자에 맞춘 작은 어댑터를 만든다.
합성 PDF를 생성하는 테스트 도구가
필요하면 `reportlab`을 개발 의존성으로만 추가한다. 구현 첫 단계에서 호환 버전을 설치·고정하며
계획 문서의 관찰용 pypdf 버전을 실제 파서 버전으로 오인하지 않는다.

| 선택 | 장점 | 비용·대안 |
| --- | --- | --- |
| 직접 연결한 고정 파이프라인, 채택 | 단계별 입출력과 장애가 드러나고 의존성이 적음 | 연결 코드를 직접 관리해야 함 |
| LangChain 기반 고정 RAG | 로더·검색·모델 교체용 공통 인터페이스 활용 | 작은 초기 범위에 별도 추상화·버전 의존성 추가 |
| 에이전트 기반 검색 | 복합 질문의 반복 검색에 유연 | 실행 횟수와 실패 경로가 늘어 이번 평가 범위를 벗어남 |

LangChain은 RAG의 필수 조건이 아니다. 먼저 자체 계약으로 흐름을 검증하고 필요하면 어댑터에서 도입한다.
범용 플러그인 체계는 만들지 않는다. 파일·함수는 책임에 맞게 나누되 빈 계층부터 생성하지 않는다.

```text
PDF --> parse + review --> DCT/common chunks --> OpenAI embeddings --> FAISS
                                                                         |
question + vehicle --> profile check --> OpenAI query embedding --> top-k <+
                                                                     |
                                                                     v
                                              evidence --> OpenAI Responses
                                                                     |
                                                                     v
                                                      citation check --> CLI
```

구현 예정 경로는 `src/avante_manual_rag/` 아래 `ingestion/`, `parsing/`, `indexing/`,
`retrieval/`, `answering/`, `adapters/`, `evaluation/`, `contracts.py`, `cli.py`다.
`tests/`는 합성 회귀 테스트, `evals/`는 직접 작성한 평가 질문·판정 기준을 둔다.
실제 생성한 경로만 구현 시 README와 AGENTS.md에 반영한다.

### 2. PDF 추출과 검토 기록

| 선택 | 장점 | 한계 |
| --- | --- | --- |
| pdfplumber의 문자 좌표·표 추출, 채택 | 열·행·영역 단위 검사와 시각적 비교에 활용 가능 | 한국어 다단 순서와 복잡한 표의 정확성은 샘플로 검증해야 함 |
| pypdf 텍스트 추출 | 탐색에서 한글 추출을 확인했고 단순 텍스트 처리가 간단 | 텍스트 존재만으로 표의 셀 관계를 입증하지 못함 |
| OCR 또는 문서 이해 모델 | 스캔·그림을 처리할 여지가 있음 | 별도 의존성·오류 평가·실행 비용이 필요하므로 후속 범위 |

파서는 페이지별로 원문 텍스트와 좌표 블록, 제목·표·각주·경고를 추출하고 절의 순서를 연결한다.
표 영역의 텍스트가 일반 본문으로 다시 색인되지 않도록 영역을 구분한다.
도안 식별자·반복 머리말 제거는 위치와 반복 패턴으로 제한하고 원문 필드는 보존한다.
페이지 번호는 페이지별 실제 표기에서 확인하며 전체 문서에 `PDF 번호 - 6` 같은 규칙을 적용하지 않는다.

시각 검토는 PDF 13·16 및 다단 본문·DCT 절차·경고·그림 의존·빈 추출 페이지를 포함한다.
전체 436페이지에는 상태를 기록하되 시각적으로 전부 검증했다고 표현하지 않는다.
일반 추출과 별개로 `needs_review` 구간은 색인에서 제외한다.

단일 문서의 어려운 레이아웃은 해시와 영역 좌표에 묶인 로컬 검토/보정 파일로 처리할 수 있다.
보정에는 적용 근거, 검토 대상 영역, 검토 이력을 기록한다. 원본이 바뀌면 보정을 무효화한다.
답변에 맞춰 수치나 문장을 만들어 넣지 않으며, 보정 파일과 추출 전문은 생성 데이터로 취급한다.
이는 자동 OCR 추가와 달리 현재 명세의 추출·검토 경계 안에 있다.

### 3. 공통 데이터 계약과 사양 판정

외부 입력은 타입 선언 외에 필수 필드, enum, 페이지 범위, 해시 형식, 경로를 검사한다.
최소 계약은 다음과 같다. 추가 필드는 실제 필요가 확인될 때 도입한다.

| 계약 | 필수 의미 |
| --- | --- |
| VehicleProfile | `project_code`, `model_year`, `transmission`; 추가 옵션은 미확인으로 유지 |
| Document | 원본 해시 기반 `document_id`, 파일명·문서명·차종·연식·언어·크기·출처 원문·검증 상태 |
| Page | `document_id`, 1-based `pdf_page`, nullable `printed_page`, 처리 상태와 오류·미처리 영역 |
| Block | 결정적 ID, 페이지·좌표·절 경로, 본문/표/경고/각주 종류, 원문과 정규화 표현, 검토 상태 |
| Table | 행·열·단위·셀 값 및 각주/경고 ID; 셀 또는 행별 적용 범위 |
| Applicability | `common / dct / manual / unknown`, 판정 근거, 추가 조건; 혼합 내용은 별도 하위 블록 |
| Chunk | 블록 ID들, 페이지 목록, 절 경로, 적용 범위, 본문 및 필수 경고·각주 참조, 설정 지문 |
| IndexBuild | 파싱·청크 세대, 제공자·모델 ID·공개 버전·차원·전처리, 프로필, 인덱스/JSON 해시·항목 수, 활성 여부 |
| SearchResult | 청크·근거 묶음, 순위 점수, 적용 조건, 데이터 세대와 누락 요약 |
| Answer | 상태, 주장별 텍스트·근거 ID·발췌문, 프로그램이 구성한 인용, 누락·조건 안내 |

`common`은 'DCT라는 단어가 없음'이 아니라 확인된 공통 절·공통 행에만 부여한다.
제목·절 경계·행 라벨과 검토한 범위 규칙으로 분류하고 원문 근거를 남긴다.
불명확하면 `unknown`이다. 수동과 DCT 설명이 한 페이지에 있어도 페이지 단위로 일괄 분류하지 않는다.
공통 표 제목과 주의는 DCT 행에 연결하되 수동 전용 행은 DCT 근거 묶음에 포함하지 않는다.
N 전용 기능도 모두 DCT 전용이라고 가정하지 않는다.

옵션·주행 조건은 변속기와 별도 조건으로 유지한다. 필요한 옵션이 미확인일 때는 조건부 설명이나
추가 확인을 반환한다. 초기 지원 프로필 외의 입력은 지원 범위 밖으로 표시한다.
시험 데이터에는 다른 차량·연식·변속기를 포함해 필터가 실제 작동하는지 검증한다.

### 4. 청크·임베딩·저장소

기본 청크는 절과 의미 블록 단위로 만든다. 긴 본문은 문단 경계에서 나누고 제목·필수 경고를 연결한다.
표는 전체 표 또는 행 묶음을 사용하되 각 조각에 필요한 열 제목·단위·각주를 복원한다.
여러 페이지에 이어지는 표·경고는 관련 페이지 목록과 연결 ID를 유지한다.
한도를 넘는 표는 무작정 잘라 넣지 않고 행 묶음으로 다시 만들거나 검토 필요로 남긴다.
단순 고정 글자 수 분할은 쉽지만 이 문서의 표 조건을 잃기 쉬우므로 주 전략으로 사용하지 않는다.

임베딩은 텍스트를 검색용 수치 벡터로 바꾸는 과정이다. OpenAI Embeddings API와
`text-embedding-3-small`을 사용한다. 초기 차원은 기본값인 1,536으로 설정에 명시한다.
청크와 질문에 같은 모델·차원·전처리 정책을 적용한다. 임베딩 입력은 tiktoken으로 길이를
확인하고 요청별 입력 개수·합계 토큰을 API 제한 안에서 묶는다. 빈 문자열은 전송하지 않는다.
한도를 넘는 청크는 의미 단위로 재분할하거나 검토 필요로 남기며 임의로 잘라 전송하지 않는다.
응답의 index로 입력 순서를 복원하고 개수·차원·유한값·영벡터를 검사한다.
청크 텍스트 해시·모델 ID·차원·전처리 버전으로 벡터를 로컬 캐시하여 동일 청크의 재호출을 줄인다.
모델 제공자가 가중치 digest를 제공한다고 가정하지 않는다. 요청/응답 모델 ID와 공개 버전만
기록하고, 별칭의 서버 내부 변경을 완전히 감지하거나 원격 응답을 비트 단위로 재현할 수 있다고 주장하지 않는다.
의미 검색 대신 문자 n-gram/키워드 검색을 쓰면 모델 없이 재현하기 쉽지만 표현이 다른 질문에
불리할 수 있다. 이번에는 의미 검색을 기본으로 하며 키워드 혼합·reranker는 도입하지 않는다.

| 저장 방식 | 선택 이유 또는 보류 이유 |
| --- | --- |
| FAISS CPU + JSON 메타데이터, 채택 | 사용자가 선택한 로컬 벡터 검색, DB 서버 없이 구성하고 메타데이터를 직접 확인 가능 |
| SQLite에 벡터 저장 후 직접 계산 | 저장 트랜잭션은 편리하지만 벡터 검색 코드를 별도 구현해야 하므로 이번 선택에서 제외 |
| 메타데이터 필터를 제공하는 서버형 벡터 DB | 다중 차량·대규모 운영에 유리할 수 있지만 서비스 설치와 운영 범위가 늘어남 |

FAISS는 벡터 유사도 검색 라이브러리이며 문서·페이지 메타데이터를 보관하는 DB를 대체하지 않는다.
초기에는 `IndexFlatIP(1536)`로 정확 검색하고 IVF/HNSW 같은 근사 검색이나 GPU는 사용하지 않는다.
문서·질문 벡터를 float32로 변환하고 L2 정규화하여 내적 점수를 코사인 유사도로 사용한다.
`index.faiss`에는 벡터를, JSON에는 FAISS 행 번호에서 청크 ID·원문·페이지로 가는 매핑을 저장한다.
벡터 수와 JSON 매핑 수가 일치해야 하며 검색 결과 `-1` 행은 근거로 사용하지 않는다.

사양 필터는 top-k 이후가 아니라 색인 대상 선정에 적용한다. 지원 프로필 CN7N/2025/DCT의
검토된 DCT 및 공통 청크만 넣는 프로필 전용 색인을 만들고 질의 프로필과 인덱스 프로필을 대조한다.
수동·미확인·다른 연식 청크는 이 인덱스에 넣지 않는다. 이 구조는 최초 단일 프로필에 한정하며,
여러 프로필을 한 인덱스로 확장할 때는 별도의 사전 필터 설계가 필요하다.
필터로 제외된 구간과 추가 옵션 조건은 JSON 메타데이터에서 계속 추적한다.

top-k 기본값은 5다. 동점 결과의 표시 순서는 청크 ID로 정렬하며 근거 부족과 빈 색인을 구분한다.
최소 점수는 모델별로 대표 질문에서 조정하고 지문에 기록한다. 높은 점수는 답의 근거 충분성을
보장하지 않으므로 생성 단계에서도 근거 부족 판정을 허용한다.

원본 위치와 데이터 출력 루트는 설정으로 받는다. 저장소는 다음 데이터 세대를 분리한다.

- 파서/보정 변경: 페이지·블록부터 청크·벡터까지 재생성.
- 청크/사양 규칙 변경: 원본 파싱 결과를 재사용하고 청크·벡터 재생성.
- 임베딩 제공자·모델 ID·공개 버전·차원·입력 정책 변경: 청크 재사용, 벡터 캐시와 색인 새 세대 생성.
- 생성 모델·프롬프트 변경: 색인 재사용, 답변 평가 재실행.

원본 해시·설정 지문·블록 범위로 결정적 ID를 만든다. FAISS와 JSON은 동일 생성 ID의 새 디렉터리에
완성하고 파일 해시·벡터 수·매핑·프로필·모델 설정을 검증한 뒤 로컬 활성 포인터 파일 하나를
원자 교체한다. 독자는 포인터를 한 번 읽고 그 세대의 불변 파일만 연다. 기존 세대는 유지한다.
여러 파일의 동시 교체나 정전 내구성을 보장한다고 주장하지 않으며, 불완전한 세대는 활성화하지 않는다.
한 권 규모에서는 항목별 삭제·수정보다 전체 프로필 색인을 새로 만드는 방법을 사용한다.
원본·생성 데이터·색인은 출력 루트 안에서만 다루고, FAISS 파일은 앱이 생성한 로컬 파일만 읽는다.
read_index 전에 저장된 크기·해시를 검사한다. 해시 대조는 손상 검출이며 출처 불명의 파일을
신뢰 가능하게 만드는 수단은 아니다. JSON 대신 pickle 기반 문서 저장 형식을 사용하지 않는다.

### 5. OpenAI SDK와 API 키·비용·데이터 전송

| 선택 | 장점 | 비용·한계 |
| --- | --- | --- |
| OpenAI API + 공식 SDK, 채택 | 로컬 모델 설치·튜닝 없이 사용자 요청 스택으로 빠르게 연결 | 네트워크·키·과금·계정 한도와 텍스트 외부 전송 필요 |
| Ollama 등 로컬 모델, 대안 | 문서·질문을 로컬에서 처리 가능 | 모델 다운로드·하드웨어·품질 조정 부담이 있어 이번 구현에서 제외 |

`OPENAI_API_KEY`는 환경변수 또는 로컬 `.env`에서 읽으며 환경변수가 우선한다.
소스·설정 예시·로그·대화에 실제 키를 넣지 않는다.
`embedding_model=text-embedding-3-small`, `embedding_dimensions=1536`을 예시 설정에 둔다.
`chat_model` 또는 `OPENAI_CHAT_MODEL`은 실제 생성 시 필수다. 사용자가 지정한
`gpt-5-mini`를 기본 설정에 사용한다. Responses API와 Structured Outputs를 실제 호출하여
요청/응답 모델 ID·SDK 버전·입력/출력 한도를 기록한다.
등록·파싱·캐시된 FAISS 로드는 키 없이 가능하다. 새 임베딩·질문 임베딩·생성에는 키가 필요하고
search에는 생성 모델 설정을 요구하지 않는다.

색인 시 처리할 청크 전체가 OpenAI 임베딩 API에 전송되고 질의 시 질문이 추가 전송된다.
생성 시 질문·차량 조건·검색한 근거를 전송한다. 원본 PDF는 로컬 파싱하며 Files API에
업로드하지 않는다. 원본과 파생 전문 데이터는 Git·패키지·배포 대상에서 제외한다.
Responses 호출은 `store=false`를 사용하되 이것이 서비스의 모든 보관을 없애는 보장은 아니라고
명시한다. 실제 데이터 보관 정책은 공식 API 데이터 제어 문서를 따른다.

비용은 임베딩할 토큰 수와 질의/생성 사용량에 따라 달라진다. 총액은 실제 사용량 확인 없이
확정하지 않는다. API usage를 단계·모델별로 기록하고 선택한 모델의 공식 단가와 함께
설명한다. 캐시와 작은 초기 평가로 반복 임베딩 비용을 줄이고 비용 추정을 위한 토큰 수를 남긴다.

SDK의 요청 timeout을 명시하고 `max_retries=0`으로 설정하여 재시도를 어댑터 한 곳에서 관리한다.
초기 재시도 상한은 2회, 대상은 연결 오류·일시적 rate limit·재시도 가능한 서버 오류다.
인증·권한·잘못된 입력·모델 부재·할당량 소진과 잘못된 응답은 즉시 명확하게 실패시킨다.
전체 작업 기한도 제한하고 임베딩 장애와 생성 장애를 구분한다.

### 6. 답변·인용 검증과 입력 예산

OpenAI Responses API에 스트리밍 없이 `store=false`, `text.format`의 strict JSON Schema
응답 계약을 전달한다. 거부(refusal)·incomplete·잘못된 출력은 정상적인 근거 답변으로 처리하지 않는다.
모델은 주장마다 근거 ID와 짧은 원문 발췌를 돌려준다. 페이지 번호·문서명·URL을 모델이 만들게
하지 않고 저장된 근거 ID에서 프로그램이 인용을 구성한다.
JSON 형식이 맞아도 내용이 참이라는 보장은 없으므로 다음 검사를 분리한다.

1. 구조·참조 검사: 필수 필드, 허용 상태, 반환 ID가 실제 전달 근거에 포함되는지 확인.
2. 발췌 검사: 공백 정규화 외에 수치·단위를 바꾸지 않고 원문과 일치하는지 확인.
3. 수치·경고 검사: 숫자·단위가 연결된 근거에 있는지 검사하고, 표의 선택된 행·조건과 필수
   경고는 원문 기반 표시 항목으로 함께 출력. 일반적인 숫자 집합 포함 검사만으로 표의 관계를 보장하지 않음.
4. 의미 검토: 16개 평가 사례의 주장·수치·조건·인용 대응을 원문과 비교해 사람이 판정.
   자동 검사 통과를 의미적 검증 완료로 부르지 않음.

잘못된 인용을 검출하면 재생성을 반복하지 않고 `citation_validation_error`를 반환한다.
답변 상태는 `answered`, `insufficient_evidence`, `needs_clarification`, `conflicting_evidence`와
오류 `configuration_error`, `retrieval_error`, `generation_error`, `citation_validation_error`로 구분한다.
앞의 네 상태는 정상적인 도메인 결과, 오류는 CLI 비정상 종료다.

문맥에는 본문뿐 아니라 질문·시스템 지시·출력 예약 공간까지 반영한다. 모델별 입력 예산을
설정하고 준비 단계에서 한도와 잘림 동작을 확인한다. 완전한 근거 묶음부터 선택하며 모델 입력이
잘렸거나 완료되지 않은 경우 정상 답변으로 인정하지 않는다. 충분한 근거 묶음이 들어가지 않으면
부족 상태를 반환한다. 저장된 청크는 이 과정에서 변경하지 않는다.

### 7. CLI·평가와 완료 판정

구현할 명령군은 `ingest`, `index`, `search`, `ask`, `evaluate`다. 설정은 TOML 및 환경변수로
받으며 데이터 경로·차량 프로필·모델·기한·검색/문맥 설정을 분리한다.
도움말과 문서에는 실행 예시를 넣되 지금 존재하는 명령으로 표현하지 않는다.
`search`는 생성 모델 없이, `evaluate`의 기본 회귀 모드는 실제 모델 없이 동작하도록 한다.
기본 로그는 단계·문서 ID·오류 요약으로 제한한다.

빠른 구현 순서는 대표 페이지의 본문·표·사양 사례를 먼저 처리하고, 각 범주 1개씩 4개의
질문으로 OpenAI 임베딩 -> FAISS -> OpenAI 생성 -> 인용 검사를 연결하는 것이다.
이 초기 결과에는 처리 페이지 범위를 표시한다. 이후 같은 경로로 전체 436페이지의 상태를
기록하고 16개 평가 사례로 확장한다. 새 GUI·DB 계층·추가 모델 제공자 구현은 선행 조건으로 삼지 않는다.

평가 계약은 `rag-quality-evaluation/spec.md`를 따른다. 16개 질문은 실제 개인 대화 수집 대신
직접 작성한 사례로 구성하고 일반·표·사양·근거 부족 각 4개를 채운다.
초기 후보는 타이어 표, DCT 오일 표, 매뉴얼에서 실제 확인할 일반 기능과 DCT 절차다.
원문 확인 전 정답 수치·페이지를 만들어 채우지 않는다.
각 질문에 `answerable`, `clarification`, `insufficient` 기대 상태 및 필수 근거 묶음을 명시한다.
표의 본문과 필수 각주 등 여러 블록이 필요하면 전부 있어야 검색 성공으로 센다.

기준 지표 정의:

- Recall@5: `answerable` 사례 중 상위 5개 근거 묶음에 필수 근거가 모두 포함된 사례 비율.
- 답변 통과율: `answerable` 사례 중 필수 주장·조건을 충족하는 답변 비율. 근거가 있는데 유보하면 실패.
- 각 비율 90% 이상, 잘못된 사양·인용·수치/단위·필수 경고 오류 0건, 근거 부족 4개 모두 유보.
- 파싱 기준 사례의 필수 내용·관계 보존 및 전체 436페이지 상태 기록. 미처리 구간 의존 사례는 실패.

지표의 분자·분모, 요청/응답 모델 ID와 공개 버전, 설정·API 사용량·데이터 세대를 기록한다. 대표 세트에 맞춘 초기 기준선이며
미지의 질문에 대한 통계적 정확도 또는 안전성 보증으로 해석하지 않는다.
모의 자동 테스트와 실제 모델 평가를 모두 통과해야 전체 구현·검증 완료로 표시한다.
상세 응답·발췌·이미지는 로컬 평가 폴더에 두고 공유 요약에는 지표와 사례 ID·실패 유형만 남긴다.

## Risks / Trade-offs

- [표·다단 구조 오인] -> 시각적 샘플 비교와 해시 기반 보정, 미검토 구조의 색인 제외.
- [보수적 사양 분류로 검색 누락] -> unknown을 common으로 바꾸지 않고 절별 판정 근거와 누락 비율을 보고.
- [그림 또는 OCR 미처리] -> 페이지/영역별 상태를 공개하고 해당 근거 의존 질문은 평가 실패로 처리.
- [API 키·계정 한도·네트워크 또는 모델 품질 문제] -> 작은 실제 요청부터 접근성을 확인하고
  인증·할당량·품질 실패를 구분하며 기본 자동 테스트는 모의 API로 실행.
- [반복 임베딩 비용과 데이터 외부 전송] -> 청크 벡터 캐시, usage 기록, 텍스트 전송 범위 명시.
- [FAISS와 JSON 불일치] -> 동일 생성 ID의 불변 묶음을 검증한 후 활성 포인터만 교체.
- [인용은 존재하지만 주장을 지지하지 않음] -> 주장별 원문 발췌와 사람의 의미 판정을 별도로 수행.
- [단일 문서용 보정의 과적합] -> 원본 해시와 범위를 명시하고 다른 문서 지원을 주장하지 않음.
- [정확 검색의 성능 저하] -> 청크 수·시간·메모리를 측정하고 대규모 확장 시 저장소 변경을 별도 검토.
- [잘못 기록된 URL] -> 로컬 문서·페이지 인용은 유지하되 미검증 URL 링크를 노출하지 않음.
- [원본 유출] -> 원본·추출 전문·색인을 버전 관리와 배포에서 제외하고 테스트는 합성 PDF를 사용.

## Migration Plan

1. 프로젝트 가상환경에 pdfplumber·OpenAI SDK·faiss-cpu와 필요한 도구를 고정 설치한다.
   Windows/Python 3.11에서 import·FAISS 저장/읽기를 검증한다. 기존 PDF와 manifest는 읽기 전용 입력이다.
2. 대표 문서 메타데이터·출처 상태와 샘플 파싱을 확인하고 공통/DCT 근거를 만든다.
3. API 키·생성 모델 설정으로 실제 소규모 임베딩을 확인하고 FAISS/JSON 묶음에 검색·생성을 연결한다.
4. 먼저 4개 사례를 검증한 뒤 전체 페이지와 16개 사례로 확장하고 전체 자동 테스트를 실행한다.
5. 새 세대가 실패하면 이전 활성 세대로 복귀한다. 최초 구축 실패라면 미완료 상태로 두고 원본을 유지한다.
6. 실제 설치 버전·모델·명령·결과·한계를 README와 관련 OpenSpec 산출물에 반영한다.
   웹 배포나 외부 게시 단계는 없다.

  사용자가 아직 이름을 지정하지 않았다. API 계약에 맞는 접근 가능한 모델을 설정으로 선택하며,
  키 또는 모델 접근 권한이 없으면 실제 평가는 미완료로 남긴다. 임베딩 모델은 이미 확정됐다.
- 검토 대상 샘플에서 가장 적합한 pdfplumber 표 추출 설정과 필요한 보정 영역은 어디인가?
  파서 어댑터의 설정 선택이며 데이터 계약과 작업 구분은 바뀌지 않는다.
- 대표 문서의 공식 모델 페이지 주소를 확인할 수 있는가?
  확인 실패 시 미검증 상태로 유지하며 로컬 문서·페이지 추적을 통해 초기 동작을 검증한다.

## 구현 버전과 현재 계약

Python 3.11.9, pdfplumber 0.11.10, openai 3.26.0, faiss-cpu 1.15.1, numpy 2.4.6,
tiktoken 0.14.0으로 구현했다. API 생성 응답 모델은 `gpt-5-mini-2025-08-07`로 확인했다.
테스트는 pytest 9.1.1, 합성 PDF는 reportlab 5.0.1을 사용한다.
원본 해시에 묶인 로컬 검토 영역으로 표/다단 보정을 적용하며 미검토 영역은 색인에서 제외한다.
인용은 PDF 줄바꿈 공백 차이를 정규화한 뒤 실제 원문 span으로 복원할 수 있다.
strict 출력 스키마에서 주장마다 검색 근거 ID와 해당 근거의 발췌 목록을 함께 제한한다.
문장부호와 수치를 보존한 연속 발췌를 생성하며, 스키마 문자열의 줄바꿈만 공백으로 정규화한다.
외부 API 응답의 `quote_id`를 검색 근거에 연결된 발췌로 변환한 후 공통 계약의 `quote`를 검증한다.
발췌 본문을 스키마 enum에 반복하지 않고 참고 데이터에 보내 스키마의 토큰 증가를 줄인다.
의미 판정은 불변 보고서의 로컬 복사본에 기록한다.
전체 추출과 검토 완료 영역 수는 구분한다. 명령·검증·한계는 README 및
`docs/implementation-validation.md`에 기록한다.
